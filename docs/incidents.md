# 많은 공을 들인 오류와 해결 기록

이 문서는 사고를 성공담으로 바꾸지 않는다. 구현과 오프라인 검사를 마친 부분, 당시 실제 제작에서 확인한 부분, 아직 해결하지 못한 부분을 구분한다. 사례 번호는 [근거 목록](evidence/README.md)과 연결된다.

## 저장과 순서

### 1. 같은 URL에 남은 과거 문항이 새 작업에 섞임 · C02

새 검색에서 7개 ID를 선택했지만 편집·저장 화면에는 4개가 남았다. 그중 새 묶음에서 살아남은 문항은 1개였다. 나머지 3개는 과거 상태였다. 선택 수만 보면 일부 작업을 마친 것처럼 보일 수 있었지만 실제로는 상태 오염이었다.

대책은 새 작업 전에 저장 상태가 비어 있는지 확인하는 것이다. 지울 때는 공식 UI를 쓰고 재로드에서 0개를 확인한다. `다음 단계` 뒤에는 새 전체 ID 묶음을 비교한다. 사고 복구에서 browser Back에 의존하지 않는다.

이 대책은 새로 시작하는 경우에 적용한다. 기존 문제지에 이어서 추가하는 요청에서 정상 저장 문항을 지우면 안 된다.

### 2. 선택 18개가 저장 1개로 줄어듦 · C02~C03

검색 화면의 선택과 편집 화면의 보존 상태가 달랐다. 편집의 추가 검색에서는 출처 선택도 reset될 수 있었다. 조기 편집 진입 뒤 회복 검색이 어려워지는 문제가 이어졌다.

`BeforeNext`와 편집 직후 전체 ID 대조를 두었다. 검색 재진입 때 범위 칩을 다시 확인한다. 부분 저장을 승인한 작업에서는 검증된 묶음만 저장하고 미해결 목록을 유지한다. 부분 저장을 막기 위해 모든 검색의 끝을 무조건 기다리는 방식은 사용자의 요청과 맞지 않는다.

### 3. 개수가 같아도 원본 순서가 다름 · C08

106문항 제작 기록에서 앞 5문항의 순열 오류를 발견했다. 전체 ID 순서 대조로 복구한 뒤 106/106 결과를 기록했다.

저장 개수나 대표 ID만 확인하는 검사로는 이런 오류를 잡을 수 없다. target, selected, edit, persisted, reloaded의 전체 ordered bundle을 비교한다. `번호순 정렬`이 원본 프린트의 임의 순서를 재현한다고 가정하지 않는다.

### 4. 반복 원본을 같은 DB ID로 합쳐 계산함 · C09

원본의 서로 다른 위치가 같은 DB 카드에 대응했다. 같은 카드를 다시 누르는 것은 두 번째 삽입의 증거가 아니었다. 실제 관측에는 선택 해제도 있었다.

`occurrenceKey`와 `problemId`를 분리했다. distinct occurrence, 실제 duplicate/add control, 전체 occurrence 순서가 함께 있어야 반복 성공을 허용한다. 31/32와 101/102의 과거 결과에서 별도로 보존하지 못한 후행 반복 위치를 성공으로 올리지 않았다.

## 검색 누락과 본문 판정

### 5. 텍스트 검색 miss를 DB 부재로 오판함 · C03

이전 경로가 찾은 후보를 새 텍스트 검색이 다시 찾지 못했다. 이후 편집 화면에서 전체 DB 범위를 입증하지 못해 회복이 막혔다.

검색 miss 후 같은 출처 inventory, metadata, 문제지 selector, 이전 후보 지도를 확인하는 회복 단계를 추가했다. 과거 ID는 후보 단서로만 쓴다. 지금 원본과 다시 비교한다.

### 6. 빈 범위와 stale 결과를 정상 검색으로 읽음 · C05

범위가 비어 있어도 검색은 많은 결과를 낼 수 있다. 검색어 칩을 바꿔도 재검색 전 결과 수가 남아 있을 수 있다. 과거 관측에는 27개가 남아 있다가 재검색 후 6개로 바뀐 사례가 있다.

검색 전에는 실제 선택된 DB·출처와 칩을 확인한다. 검색 제출과 독립된 결과 판독을 결합한다. 빈 범위를 `전체 DB`로 해석하지 않는다. 당시 결과 수는 사례의 관측값이며 현재 검색량 계약이 아니다.

### 7. 메타데이터는 맞는데 본문은 다름 · C07·C12

연도·기관·번호가 같은 후보라도 지수나 연산자가 달랐다. 작은 기호를 한 번 읽고 본문 일치를 확정하는 위험도 있었다.

원본과 후보를 확대해서 다시 읽고 artifact와 비교 기록을 결합한다. 명확한 본문 차이는 거부한다. 끝내 불명확한 기호는 `source_anomaly`로 남긴다. 메타데이터 일치가 본문 불일치를 덮을 수는 없다.

### 8. lazy 결과의 위쪽만 보고 미발견을 닫음 · C07

검색 결과는 스크롤에 따라 더 나타날 수 있다. 첫 화면이나 일부 유력 카드만 본 상태에서 미발견을 닫으면 아래의 후보를 놓친다.

인쇄된 기관·과목·연도 정보가 있으면 metadata rescue를 수행한다. 결과가 많으면 연도와 인쇄 metadata로 나눈다. final miss에는 누적 unique inspected ID, 결과 수, 끝 구간의 안정 관측이 맞아야 한다. exact를 먼저 찾았다면 그 ID의 실제 검사 근거를 확보하고 선택으로 갈 수 있다.

### 9. `t>0`를 `양수`로 번역한 AND 칩이 exact를 배제함 · C10

원본 본문에 없는 단어를 모든 검색에 남겼다. 작은 결과군을 다 봐도 그 단어 때문에 제외된 후보의 부재를 증명할 수 없었다. 사후에 본문이 같은 후보를 발견했지만 저장 결과는 계속 22/23이었다.

칩의 출처를 literal-body, semantic-inference 등으로 구분했다. 실제 본문의 두 단어에서 시작하고 reset·backoff·후보 회복을 기록하도록 계약을 만들었다. 별도 색인 일치 근거가 없는 의미 번역은 필수 AND 제한어로 쓰지 않는다.

이 수정의 성공은 검색 계약이 잘못된 입력을 막았다는 뜻이다. 미저장 문항이 자동으로 저장됐다는 뜻이 아니다.

### 10. 단일 규칙으로 정리하다 짧은 단어 기준을 잃음 · C14

검색 계약을 단일화한 뒤 두 literal 칩이라는 조건은 남았지만 단어의 형태 검사가 빠졌다. 후속 제작의 1~32번에서 문장형 칩이 반복됐다. 보고서의 “모두 짧은 단어 사용”이라는 설명도 실제 로그와 달라 정정했다.

기본 칩에는 길이·공백·문장 형태 검사를 추가했다. optional phrase prepass는 한 번의 별도 단계로 기록하고 제거 증거를 요구한다. 문장형 칩과 공백을 없앤 문장도 거부한다. 당시 저장 결과 101/102와 잘못된 절차 설명은 서로 다른 주장으로 다뤘다.

## 검증기의 오류

### 11. 저널 파일에 이벤트가 있는데 PS7에서 0건으로 읽음 · C06

LF 분할에 음수 개수 `-1`을 준 코드가 두 PowerShell 환경에서 다르게 동작했다. PS7에서는 파일 전체가 한 요소가 되어 파싱 반복문이 실행되지 않았다.

분할 개수 제한을 제거했다. 실제 파일의 빈 값, 한 줄, 여러 줄, CRLF, 재개, 손상 tail 거부를 확인했다. 2026-09-05 수정 기록에는 PS7·PS5.1 저널 검사와 당시 전체 오프라인 runner 23/23 PASS가 있다. 이는 실제 브라우저 복구를 뜻하지 않는다.

### 12. 형식만 맞는 보고가 실제 저장 결과와 달라도 통과함 · C13·C15·C17

초기 lint는 문장의 형식과 수량 표기를 검사했다. 실제 persisted 카드와 독립되어 있어 임의 출처나 원본 수의 변경을 놓칠 수 있었다. 하나의 miss receipt를 여러 원본에 재사용할 위험도 있었다.

miss receipt를 원본 번호·occurrence와 1:1로 결합했다. 이후 제작 검증은 fixed roster, 실제 persisted-card 관측, raw DB명에서 결과를 투영하도록 연결했다. 기존 문자열 lint는 형식 검사로 유지한다. 전체 내부 보고서를 자동 생성하는 기능까지 구현했다고 주장하지 않는다.

### 13. 서로 같은 판단에서 나온 자료끼리 일치해 false green · C12

gold ID, 관측, 설명문, 해시가 모두 같은 최초 판단을 물려받았다. 일관된 거짓 설명으로 바꾸고 해시를 갱신해도 기존 scorer는 통과했다.

주장 등급을 offline-contract, dated-characterization, external-ground-truth로 구분했다. 독립 원본·후보·판정이 없으면 외부 정답 검증으로 승격하지 않는다. body-exact 외부 승격은 typed 독립 판정이 원본·후보 artifact에 결합될 때까지 막는다.

### 14. 과거 PASS가 새 입력에서도 유효한 것처럼 남음 · C11~C12

검증 코드와 자료가 바뀌어도 과거 PASS 문서가 남을 수 있었다. 개별 사고의 fixture가 전체 runner에서 계속 실행되는지도 한 곳에서 확인하기 어려웠다.

PASS 출력과 당시 입력 파일을 sidecar manifest로 결합했다. 반복·중요 lesson은 evidence, negative corpus, validator, runner label을 가진 registry로 관리한다. 독립 실패 신호가 부족한 효율 관측은 record-only로 남긴다. 모든 관찰을 강제 규칙으로 늘리지 않는다.

### 15. 새 문제지 검증은 됐지만 기존 저장 문제지에 추가가 안 됨 · C17~C18

최초 `다음 단계`의 과거 묶음을 현재 전체 선택과 비교해 추가 저장을 거부했다. 당시 최초 제작 연결의 지원 범위가 실사용 경로보다 좁았다.

`editAppendReceipt`로 이전 저장, 추가 전 전체 ID, 새 delta, 실제 추가와 확인, 전체 draft를 결합했다. 과거 Next 관측을 보존했다. 후속 기록은 production 121 assertions와 전체 runner 30게이트 PASS를 보고한다. 실제 2문항의 초기 추가 저장도 별도로 검증했다. 47문항 전체 완료와는 구분한다.

## 연결과 효율

### 16. 현재 PC의 표시명을 원격 요청으로 오판함 · C19

CLI 기본 host에 의존하거나 표시명을 해석해서 다른 연결을 고르면서 잘못된 질문과 조회가 이어졌다.

`check_aside_repl.ps1`의 기본 host를 local로 고정했다. 원격 요청 표시와 실제 사용자 요청 기록이 없으면 조회 전에 거부한다. 도구로 확인할 수 있는 화면 상태는 직접 읽도록 지침을 바꿨다. 이 검사는 원격 요청 문장의 진실성까지 독립 판단하지 않으며 모든 직접 CLI 호출을 전역 차단하지도 않는다.

### 17. 인증·통신 실패 문구를 브라우저 종료로 취급할 위험 · C17·C19

한 출력에 daemon auth 실패와 “Aside isn't running” 안내가 함께 들어갈 수 있었다. 일반 timeout이나 설치 키 오류를 사용자의 앱 종료로 단정하면 잘못된 고정 응답을 보낸다.

통신·인증 실패와 종료 확인을 구분했다. 오프라인 receipt 통과를 실제 연결 복구로 보고하지 않는다. 고정 한 줄 응답은 현재 제작 probe가 종료를 확인한 경우에만 적용한다.

### 18. 기본 샌드박스 진단 실패를 실제 설치 손상으로 읽을 위험 · C21

가상 사용자 경로와 registry를 읽은 설치 검사와 실제 Windows 사용자 환경의 검사가 달랐다. 실제 환경에서는 extension 활성과 native-host 등록이 정상인 경우가 있었다.

지원되는 실제 호스트의 읽기 전용 진단으로 구분했다. 설치 확인, 확장 표면 등록, 탭 판독, 실제 입력을 별도 단계로 확인했다. 설치 검사 통과로 제어 복구를 선언하지 않는다.

### 19. Aside의 Codex 확장 표면을 Chrome로 잘못 분류함 · C20~C21

브라우저 family 이름만 보고 Chrome로 분류한 초기 시험에 Aside 확장 표면이 섞였다.

UUID와 실제 브라우저 identity를 확인해 기존 보고서를 정정했다. 정정 전 기록도 보존했다. 최신 새 Chrome 후보 표면은 실제 Chrome identity와 결합이 끝나지 않아 확정 성능 비교에서 제외한다.

### 20. 오래된 API 호출을 추측해서 도구 오류를 만듦 · C21

Aside `snapshot`에 옵션만 첫 인수로 줘 TypeError가 났다. 현재 문서의 `snapshot(page, options)`로 고친 뒤 판독은 성공했다. 뒤의 screenshot CDP timeout은 별개 실패였다.

초기화와 호출은 현재 도구가 반환한 문서를 따른다. 한 브라우저에서 지원한 raw CDP 입력을 다른 표면에도 적용하지 않는다. 에이전트의 호출 오류와 제품·연결 오류를 분리한다.

### 21. 세 브라우저에서 반복 시간 초과 · C21 · 미해결

Aside는 저장된 15개 전체 순서 판독에 성공했지만 캡처가 실패했다. Chrome 연결 후보는 메뉴 조작에 성공한 뒤 검색 진입이 실패했다. IAB는 15개 판독 뒤 캡처·DOM·가벼운 시험 탭 생성에서 실패했다.

당시 메모리 commit 비율 약 94.3%를 관측했다. 이는 원인 후보이며 단일 원인으로 확정하지 않았다. 실제 연결을 완전히 복구했다는 결과도 없다. 반복 재설치만으로 해결을 선언하지 않는다.

### 22. 제작 중 기록 어댑터 수리와 중복 검증이 흐름을 끊음 · C20 · 미해결

검색 제출과 결과 판독은 일부 문항에서 2.2~8.5초였다. 다음 문항 검색까지는 수분이 걸렸다. 그 사이에는 본문 검토뿐 아니라 receipt 조립, locator·occurrence 수정, 출력 polling이 있었다.

15문항 AfterReload는 한 번 113.83초가 걸렸다. 추가 저장 이력을 세 경로에서 다시 검증하는 코드가 확인됐다. 그 비중은 아직 분리 측정하지 않았다.

대책은 제작 전에 관측 어댑터를 완성하고, 한 실행 안에서 동일 입력과 artifact의 검증을 재사용하는 것이다. 정확성을 지키는 cache key와 음성 대조가 필요하다. 구현과 성능 개선 증명은 남아 있다.

## 해결 상태 읽기

코드·문서 수정과 해당 오프라인 검사는 여러 사고에서 끝났다. 과거 제작 결과는 당시 보고 범위로만 남긴다. 현재 브라우저의 완전 복구, append 검증 최적화, 브라우저 어댑터 변경, 동일 조건의 처리량 비교는 아직 끝나지 않았다.
